# How it works

athena is one Claude session, the chief of staff (HQ), in a herdr space named `athena`. It turns Linear tickets into worker Claude sessions, each in its own git worktree and herdr space, and supervises them to merge-ready PRs. This page is the detail behind the README.

## The loop

![athena's red thread weaves through three workers, takes one worker's question to you, and ties off when the work merges](../assets/one-thread.svg)

athena sits in its own space with the workers as columns beside it. It launches each ticket with a launch card, and when a worker gets stuck or finishes, a watch line appears and athena acts on it. When a worker needs a decision, athena asks you in its own pane and passes your answer on. Each worker is a full Claude session, so you can also type into its column directly.

![A ticket's path: brief, a worker on its own worktree branch builds, tests and pushes, draft PR, review sends a finding back, ready](../assets/ticket-path.svg)

A ticket becomes a brief and a worker in its own worktree. The worker builds, tests, pushes and opens a draft PR. athena checks CI, has a fresh reviewer read the diff, and sends findings back until the PR is ready. Then it asks you: you merge, or tell athena to.

![athena watch: routine progress streams by quietly; athena acts on a blocked worker, a failed check, a finished worker and a moved main](../assets/watch.svg)

`athena watch` prints one line per change, and athena reacts to the ones that matter: it asks you about a blocked worker, sends a failed check back to its worker, starts a review on DONE, and asks a repo's workers to rebase when its main moves. Routine progress stays quiet.

## Remote Control

Only HQ connects to [Remote Control](https://code.claude.com/docs/en/remote-control). `athena hq` writes `remoteControlAtStartup: true` into HQ's `--settings` file and `athena spawn` writes `false` into each worker's, and settings passed with `--settings` outrank `~/.claude/settings.json`. So HQ stays reachable from your phone or claude.ai/code even without a user-level setting, and your Remote Control list holds one athena session, not one per worker. A herdr restart resumes each session with the same `--settings` file. A worker started before this change keeps its connection until it next starts.

## Always on

`athena service install` (see [Commands](commands.md#always-on)) runs herdr's server, the dashboard and the board watcher as launchd agents or systemd user units, so they restart after a crash and come back after a reboot, and a terminal that quits or crashes only detaches. herdr's job restarts the server only after a crash, throttled to once in 30 s, so `herdr server stop` stays stopped and an out-of-memory crash does not relaunch every agent at once in a loop.

`athena doctor --fix` runs every minute beside them. It is a stateless pass, not a daemon: each part fails alone, and doctor's own state is `doctor.json` (when a part went down, the repairs tried) and `health.json` (what the dashboard's health dot shows). It restarts what died, brings HQ back on its saved conversation (never a fresh one), restarts a session whose messaging socket is gone on its conversation at its next idle, sends a resumed HQ its start routine, tells a worker that herdr resumed mid-turn to carry on, and asks HQ past 60% context to write its in-flight threads and rotate. Its restarts are unattended: one never starts a fresh HQ (with no known conversation it flags instead), and when Claude answers `/exit` with "Background work is running" it cancels with Esc and tries later, so HQ's subagents and monitors and a worker's background shells keep running. The cap of three repairs an hour holds across healthy runs in between, so a part that keeps breaking is flagged, not restarted forever. It waits 90 s before acting on a missing HQ, since herdr resumes its own agents after a restart, and it checks a worker's state with herdr before acting on what its hook last wrote. A repair that keeps failing backs off and stops after three in an hour, and says so in `health.json` and with one herdr notification.

**Nothing is typed over the human.** Before athena types into a pane (an `/exit` for a restart, rotation or retire, doctor's prompts) it reads the pane's input box with its styling (`herdr agent read --format ansi`). Claude Code draws an empty box's placeholder dim, so any text that is not dim (nor a drawn cursor) is something the human typed and has not sent. It fails closed: a screen it cannot read, a dialog, bash mode's `!` prompt or anything but an empty box at the bottom counts as typing. athena waits (rotation and restart, up to `ATHENA_TYPING_WAIT` seconds, 120 by default), or leaves the pane alone. `athena retire` refuses until `--force`. Without it, an `/exit` sent while the human was mid-sentence would be joined to their text and sent.

## After a herdr restart

herdr restores its spaces when its server restarts and, with `resume_agents_on_restore`, relaunches each agent. Left alone it relaunches Claude as a bare `claude --resume <id>`, which drops the worker's `--name`, `--settings` (where `ATHENA_WORKER` lives) and `worker.md`. So athena tells herdr each worker's whole command:

- `athena spawn`, once Claude is up, reports `claude --resume <session> <the spawn's args>` with `herdr pane report-agent-session <pane> --source athena`, and records the args (`claude_args`), the session and the outcome (`resume`) in the ledger. A refusal never fails the spawn.
- Each SessionStart in the worker's own pane reports it again for the new session id (`/clear` and a resume start one), from the worker-status hook. A worker herdr already restored bare gets its full command back at its next SessionStart.
- Only HQ's own session counts: athena's SessionStart hook registers a session from HQ's pane whose id is the conversation `hq.json` knows (a resume and a compaction keep their id), the first one while it knows none, or the new id of a `/clear` in HQ's own Claude, and records it in `hq-start.json`. A `claude -p` run from HQ's Bash tool inherits HQ's environment and pane; athena's hook tells it apart by its process ancestry (another Claude above it, `hookstatus.nested`) and by its id. herdr's own Claude hook has no such check, so herdr may report a nested session's id for HQ's pane (after a `claude -p --resume X`, or a nested compaction or `/clear`). athena never takes that id on herdr's word: `athena doctor` (every minute) and `athena hq` record the id herdr reports into `hq.json`, and register its resume command, only when it is the one in `hq-start.json`, and a resume of HQ prefers `hq-start.json`'s id when it is newer than `hq.json` (a crash right after a `/clear`). The hook never writes `hq.json`; `athena hq`, its restart and its rotation record HQ's conversation from herdr right after HQ's own start.
- HQ does the same: `athena hq`, `athena hq restart` and `athena hq rotate` report HQ's whole command and keep its args in `hq.json`, and the hook reports each new session of HQ's (ATHENA_ROLE=hq) in its own pane, so HQ never comes back without ATHENA_ROLE and `hq.md`. Only HQ's SessionStart starts Python (hooks.json passes `SessionStart` to the hook); its other events stay in shell.
- The worker-status hook records how each session started (`source` in the worker's status file, and `resumed_from`, the state before a resume; `hq-start.json` for HQ), so `athena doctor` sends a resumed HQ its start routine and tells a worker resumed mid-turn to carry on. A resumed session sits idle otherwise: a SessionStart hook cannot start a turn.
- A worker that did come back bare is still known: the status hook and the mod's completion block find it by its cwd in the ledger (`athena whoami`).
- herdr gives every pane a new terminal id when it restarts, while pane ids and agent names survive. The board attaches each column to the terminal `herdr agent list` shows for the worker's name, else the one `herdr pane list` shows for its pane, and uses the ledger's id only for a worker herdr lists under neither; a changed terminal rebuilds the columns. When herdr cannot list, the sync fails and the watcher retries, with nothing moved: the ledger's ids are the dead ones after a restart.

## The watch mod

In the HQ session, `athena watch` is run by a Claude Code mod that ships in this plugin (`hooks/watch-mod/`), not by Monitor tool calls, so routine changes never reach HQ's chat. The mod is active only where `ATHENA_ROLE=hq` (which `athena hq` sets); workers and every other session load it and see no change.

- It runs `athena watch --tagged` for the whole session and restarts it if it exits (5 s, backing off to a minute). There is no 30-minute expiry to re-arm.
- Each line is marked actionable or routine by `watch.classify`. Actionable lines wake HQ with one short prompt, a stamped header and one event per line, such as `athena watch 22:19:` then `abc-101 report DONE`: a report (DONE, DONE_WITH_CONCERNS, BLOCKED, NEEDS_CONTEXT), a worker turning blocked or exiting, a PR opened, merged or closed, failing checks, CHANGES_REQUESTED or APPROVED, new review comments, a live worker's open PR turning CONFLICTING (`<w> pr conflicts #<n>`, once per turn: GitHub's UNKNOWN while it recomputes after main moved keeps the last value, and the PR turning MERGEABLE again is a routine `<w> pr mergeable #<n>`), `main moved` (only under config `watch_main_moved` `active` or `always`), a workflow starting to fail on a repo's main, once per incident (`main ci failed`), new Slack messages for the human (`slack-new`), a stacked PR merged or newly CONFLICTING, an unexpected `gone from the ledger`, a live session (HQ or a worker) whose messaging socket file is gone (`<name> messaging socket missing`, once per turn: SendMessage to it fails until it restarts), a worker that failed to start, a live worker's PR ready to post for review (`<w> post for review #<n>`, only with config `open_prs_channel` set: at most once per PR, the bottom of a stack only, and once more after 30 minutes while it is not recorded as posted), and watch errors. Lines that arrive within a few seconds, or while HQ is running a turn, go out together once HQ is idle. The same line is told once in ten minutes (a `slack-new` ring is always told: each one is new messages) unless the worker (or stacked PR) changed in between: a routine line about it lets its events be told again, so a check that fails, goes pending after a fix and fails again wakes HQ twice, while a repeat with no change between wakes it once. What was told is remembered across a mod reload and an HQ restart.
- Some actionable lines are kept from HQ altogether, by the quiet rules in `watch.verdict` (`classify` says `quiet`): they are never printed, under the mod or the Monitor fallback, and go to `logs/watch-suppressed.log` in the state dir instead, one line each with a timestamp and the reason, rotated to `.1` at 1 MB. `<repo> main moved` is logged under config `watch_main_moved` `conflicts`, the default (HQ hears `pr conflicts` when it matters) or `never`; under `active` it is told only while the repo has a live worker working or blocked, or a live worker's open PR not yet approved, and under `always` always. `<w> pr conflicts #<n>` is told in every mode, but for a worker `athena retire` is retiring; a retired worker's PR says nothing. `<w> review comments +N` counts only comments and review bodies by humans other than the PR's author: `github-actions`, `github-advanced-security`, Copilot, `linear-code`, `sun-merge-queue`, any `[bot]` login and accounts typed Bot never count, and a burst of theirs alone is logged. `<w> state ...->exited`, `<w> gone from the ledger` and `<w> messaging socket missing` are logged for a worker `athena retire` is retiring or retired (retire marks `retiring` in the ledger before it stops the Claude, and clears it if it stops short of retiring). `<w> report DONE` or `DONE_WITH_CONCERNS` identical to the worker's last report (same status and head) is logged; a new head is told. A failed CI run of a workflow whose incident is already open is logged (`CI incident open since run <id>: <n> failed runs`). Blocked workers, BLOCKED and NEEDS_CONTEXT reports, failing checks, CHANGES_REQUESTED, a PR opened, `main ci failed`, `dash-queue` and watch errors are always told. So is `slack-new`, but for a DM the human is replying in: the doorbell marks it `slack-new <dm> <n> dm active` while the human wrote there within config `slack_dm_active_minutes` (15 by default, `0` off), and that line is logged (`human active in DM`).

### Security: the allowlist

Because HQ reads a wake as the person's own words, every line is rebuilt from an allowlist before it goes out: worker names as the ledger spells them (`^[a-z0-9][a-z0-9_-]{0,31}$`), fixed state, report, check and review words, PR numbers as `#n`, counts as integers, Slack conversation ids, CI run ids, and a CI workflow name folded to letters, digits, `.`, `_` and `-` (32 at most). Free text (a `goal not sent` reason, an exception, a branch name, a PR URL's owner and repository) is cut to its allowlisted part, and a line it cannot rebuild goes out as `a watch line not shown here (athena status)`. Each regex is anchored.

### What the mod draws

- The band above the prompt draws the last wake as athena's own row, `∞ athena 22:19` then one event per line, until the human next types a prompt.
- The prompt is submitted `asUser`, so the transcript row shows just the prompt, under Claude Code's `› Prompt from the athena plugin` label, without the frame and the "This is how Claude Code surfaces a prompt a plugin submits…" sentence that a framed plugin prompt carries. Claude Code 2.1.296 raises no `ui.render` for a plugin's prompt row, so the mod cannot redraw it yet; its `UserMessage` hook draws a compact `∞ athena 22:19 <event>` row once a build does.
- Routine lines (working and idle flips, pending or green checks, `done->idle`, the `watching:` line) only update athena's status band above HQ's prompt, such as `∞ athena abc-9 blocked · #42 #43 #45 need you · pr47 working · ✓ abc-101, abc-102 done`: athena's mark in madder, then what needs the human in the theme's warning colour (blocked, NEEDS_CONTEXT and exited workers, then the PRs whose move is the human's), the active workers by state (a DONE worker whose PR waits on HQ's review is `in review`, not done), and the done ones in the success colour. Narrower, the done ones fold to a count first (`✓ 2 done`), then the active ones, the PRs and the needs. The PRs are those whose dashboard row is in Needs you, each once: no reviewer requested where a review is required, approved (or needing no review) and waiting on the human's merge or go, changes requested or checks failing with no live worker on it, and a teammate's PR that asks the human for a review. A PR awaiting a teammate's review, in a merge queue or with auto-merge on is not counted, nor one whose worker is blocked (the worker is) or still working, and asks add none. While `athena dash` runs, a dim `open dash →` ends the line, a masked link to the dashboard's URL as `athena dash show` reads it; it is the first thing to go as the line narrows, before any name or `#n` folds. The model never reads the band.
- Links: every `#n` the mod draws (the band, its wake row, a worker's completion block) is a masked link to `https://github.com/<owner>/<repo>/pull/<n>`, the repo taken from the ledger (a live worker's or a retired worker's origin remote, the stack's repo in `stack.json`, or the repo athena searched for review requests), never from a URL a worker, GitHub or a PR wrote; a PR with no known repo, one two repos share, or one only an ask names draws as plain `#n`. Links are drawing only: the wake prompt stays plain text. Claude Code draws OSC 8 links only for terminals it knows, and herdr is not one though it renders them, so `athena hq` sets `FORCE_HYPERLINK=1` in HQ's settings; where the mod reads that the terminal gets no masked links (a worker in herdr, say), it draws plain text instead of the engine's raw-URL fallback.
- In a worker (`ATHENA_WORKER` set, or else `athena whoami` finds the session's cwd in a live worker's worktree), the `ATHENA-REPORT` line its final message ends with draws as a completion block: athena's mark and the status in its colour (Done green, Done with concerns yellow, Blocked red, Needs context orange), the PR as `#n` (a masked link into the worker's own repo, from its origin remote, where the terminal draws one), the head, the verify line, the decisions and the concerns (yellow). Drawing only: the stored message, the status hook's parsing and what athena reads are unchanged, and a line that does not parse is drawn as is.
- Monitor rows in HQ's transcript (from before the mod, or from the fallback) are drawn as nothing, in HQ only: the call, its result, and its `Monitor event:`, stream-ended and expiry notifications. The model still reads them; ctrl+o still shows the notifications.

### Stacked PRs

`athena stack set <owner/repo> <pr> ...` lists a chain in `stack.json`; `athena watch` follows each PR's state, base and mergeability every two minutes.

### Doorbells: CI and Slack

So that HQ wakes when something changed instead of sweeping on a timer, `athena watch` also rings for two things outside the workers:

- **Failed CI on main, one incident per workflow.** Every two minutes (its fetch tick), for each repo it watches for `main moved` and each repo in config `ci_repos` (a path or an `owner/name`, checked with no live worker on it), it asks `gh run list --branch <default> --status completed` for the newest runs and their conclusions. A pull request's run is left out (its branch can be a fork's `main`). The first failed run of a workflow opens that workflow's incident and says `<repo> main ci failed <workflow> <run-id>`, which wakes HQ. While the incident is open, more failed runs of the same workflow (every later push, say) wake nobody: each goes to `logs/watch-suppressed.log` with the incident's run count. A rerun of the run that opened it failing again is told, as `... <run-id> (attempt <n>)`, since HQ asked for it. When the workflow's newest completed run passes, the incident closes with `<repo> main ci recovered <workflow>`, a band line that wakes no one. Cancelled and skipped runs neither open nor close one. `ci-failed.json` in the state dir keeps the runs seen and the open incidents, so a restarted watch tells nothing twice. A repo looked at for the first time records its failures and opens an incident for each workflow whose newest run failed, without telling them, and a failure older than a day that the watch missed while it was off is recorded, not told.
- **Slack.** At start the watch reads the human's read-only Slack user token from the macOS Keychain (`security find-generic-password -s athena-slack -w`); with no such item it says `slack doorbell off: no athena-slack keychain item` on stderr and carries on. About once a minute it asks for messages newer than the last one it saw in the human's DMs and group DMs, the channels in config `slack_channels` (channel ids added to config.json by hand; none by default), and, while `slack_ext_channels` is true, every `ext-` channel the human is a member of. It says `slack-new <channel-id> <n>`, with ` dm` after it for a DM or group DM: the conversation's id and how many new messages, never their text, author or link. It counts top-level messages and replies in threads the human started (seen since the doorbell started, followed for two days); a reply in a thread the human only joined is not counted, so the fallback sweep still reads those. The human's own messages, bots and apps (except the ids in `slack_allow_bots`) and joins, edits and deletions do not count. A DM or group DM the human wrote in within the last `slack_dm_active_minutes` (default 15; `0` turns this off) is a conversation they are having: its new messages ring `slack-new <dm> <n> dm active`, which the watch keeps out of HQ and logs to `logs/watch-suppressed.log`; when the window lapses with messages after the human's last one still unanswered, it rings `slack-new <dm> <n> dm` once with their count, so nothing is lost. A DM the human has not written in recently rings as before. It reads only each message's author and ts for this. The very first poll starts every conversation at now, so history never rings; after that, a conversation seen for the first time (a new DM, which Slack lists only once it has a message, or a channel added to the config) is read from the last completed poll, so its first message counts. A poll reads at most 40 conversations: up to 12 channels (more take turns), then the DMs. Slack's `conversations.list` gives no date for a DM (measured: none of 41), so the doorbell learns each DM's last activity from one first read of its newest messages, then reads every DM active in the last week on every poll (in turn, if there are more than the reads allow), and the quieter ones in turn. With 41 DMs, 6 of them active this week, an active DM is read every poll: a new message there rings within about a minute. It runs on a thread of its own, so a slow Slack never holds up the watch. A rate limit waits out Slack's Retry-After, a network error backs off up to 15 minutes, a channel Slack refuses is left alone for an hour, and an error that means the token no longer reads (revoked, a missing scope) is a watch error, told once. What it keeps, in `slack.json` in the state dir, is the last-seen ts per conversation and thread, the counts not yet rung, and per DM the ts of the human's last message and how many came after it. The token is used only in the Authorization header of read methods (`auth.test`, `conversations.list`, `users.conversations`, `conversations.history`, `conversations.replies`), and never printed, logged or written.

The mod tells every `slack-new` ring (the watch already keeps what it counted across restarts); a DM's ring wakes HQ at once, while a channel wakes it at most once in five minutes, what it rings in between adding up into that next wake. Rings for one conversation that wait together add up into one line, right after a `dash-queue` ring, and the eight-line cap never cuts a ring. HQ reads the conversation's newest messages; it does not move `sweep.json`'s shared `oldest`, which only the 2-hourly fallback sweep does. A `main ci failed` line follows the usual ten-minute rule; a workflow's repeat failures never become lines at all. To try the Slack side once, with a scratch state dir so nothing touches the running watch's: `ATHENA_STATE_DIR=$(mktemp -d) ATHENA_CONFIG=~/.local/state/athena/config.json athena watch --slack-once --window 900` prints the `slack-new` lines of the last 15 minutes (a DM you wrote in lately goes to that scratch dir's `logs/watch-suppressed.log` instead).

### Fallback

The watch mod needs Claude Code 2.1.286 or later. If the mod is not loaded (Claude Code older than 2.1.286, mods turned off, or the plugin not reloaded since an update; `pgrep -fl 'athena watch --tagged'` shows nothing), HQ arms Monitor with `athena watch` itself and re-arms it every 30 minutes, as the `athena` skill says.

To try the mod without real workers, see [Development](development.md#try-the-watch-mod).
